# Общий поиск Underwood: контекст для реализации

Подготовлено 21 октября 2026 года. Это задание для реализации уже согласованного дизайна. Исходники приложения при подготовке документа не менялись. Готовый запрос для нового чата — [PROMPT.md](PROMPT.md).

## 1. Результат, который нужен пользователю

Поиск растений доступен с любой страницы через общую шапку. При открытии и вводе показывается отдельная быстрая выдача; текущая страница, её товары, фильтры, URL и прокрутка при этом не изменяются. Только Enter, лупа отправки или кнопка полного каталога применяют запрос к каталогу.

Важнейшая особенность: одно растение/сорт может иметь несколько реальных предложений: размер + горшок, возраст + горшок или только горшок. Быстрая выдача должна помогать выбрать конкретное предложение, а не просто повторять название и цену «от».

Пользователь уже утвердил направление, размещение поиска и компактность полей. Повторный выбор между кнопкой и полем не нужен. Реализация начинается с мобильной версии, затем адаптируется к планшету и десктопу. Это локальная реализация с проверкой в браузере; деплой не входит в задачу.

## 2. Утверждённые решения

**Последняя правка пользователя — уменьшение высоты:** десктоп48 → **36 px**, планшет48 → **40 px**. Телефонные макеты остались48 px. Текст в поле16 px, иконки центрированы; уменьшать читабельность для экономии высоты не нужно.

Начальная граница десктопной однострочной шапки —1100 CSS px; до1099 поиск второй строкой. Полную навигацию сохранять там, где она помещается; для телефона использовать существующее меню. Проверять переходы около768 и1100 и реальное помещение контента, а не только имя устройства. На1100 поле должно помещаться примерно в316 px или шире. Координаты эталонов не означают абсолютную вёрстку страницы: на других ширинах использовать контейнер и адаптивную компоновку.

На телефоне и планшете поле второй строки уходит при прокрутке вместе с документом. Первая строка остаётся закреплённой. Когда поле полностью вне видимой области, в зарезервированном месте первой строки появляется лупа; при возвращении — скрывается. Не менять высоту документа и не сдвигать логотип/меню. Во время активного поиска это переключение не переносит фокус. На десктопе поле остаётся в закреплённой шапке постоянно.

### Быстрая выдача и предложения

- Группа — одно растение/сорт, с изображением и названием.
- Свёрнутая группа показывает **самое дешёвое доступное конкретное предложение**: размер/возраст, если есть, горшок, точную цену BYN и «В наличии». Пример: «20–30 см · горшок P9 — 5 BYN». Цена должна относиться к показанным параметрам.
- Если предложений несколько, отдельная кнопка «Ещё N» раскрывает остальные вместе с показанным. N = общее число реальных предложений группы минус1. При единственном предложении кнопка не нужна.
- В раскрытой группе каждая строка показывает реальную комбинацию, её цену, наличие и ссылку на выбранное предложение. «Под заказ» — также реальное предложение и доступная ссылка, не скрытая/заблокированная строка.
- Не создавать независимые переключатели горшка и размера/возраста в выдаче: они могут образовать сочетание, которого нет в БД.
- Раскрытие/сворачивание сохраняет порядок растений и положение выбранной группы. В частности, раскрытая Даника остаётся после Смарагда, а не перемещается первой. Раскрывать одну группу за раз; это правило реализации для предсказуемой высоты.
- Счётчики различают растения и предложения: «10 растений · 23 варианта». Число растений не равно числу строк вариантов. Склонения русских слов корректны для1/2/5/21 и т. п.
- Окно растёт по содержимому до доступной высоты. На низком экране прокручиваются результаты; поле и кнопка перехода в каталог остаются доступны. В desktop-эталонах высоты688/848/800/628 — размеры показанных состояний, **не обязательные фиксированные высоты в CSS**.
- Нажатие на название/свёрнутую основную строку открывает показанное конкретное предложение; на «Ещё» — только раскрывает. Не вкладывать кнопку в ссылку или делать одну область с конфликтующими действиями.

## 3. Состояния и URL: правила реализации

Основной контракт выше утверждён пользователем. Детали этого раздела дополняют его для реализации и не являются новыми макетами.

Разделить `draftQuery` в панели и `appliedQuery` каталога. Ввод и очистка черновика не меняют карточки позади, фильтры или `q` в URL. Открывая поиск из каталога с `q`, предзаполнить черновик применённым запросом. На других страницах начинать с пустого запроса; не вводить историю поиска/localStorage в эту задачу.

| Действие | Результат |
| --- | --- |
| Нажать поле/лупу в шапке | Открыть поиск, перевести фокус в реальный input. Первый введённый символ не теряется. |
| Ввести/очистить текст | Обновить только быструю выдачу; очистка остаётся внутри панели. |
| Закрыть крестиком/Escape; на десктопе нажать подложку | Закрыть без применения черновика, сохранить исходные страницу, URL, фильтры и прокрутку; вернуть фокус инициатору. |
| Enter / лупа / «Все N растений в каталоге» | Одна общая функция отправки: trim запроса, закрыть панель, применить `q` и сбросить страницу каталога на1. |
| Отправить из каталога | Сохранить категорию, горшок, диапазон цен, наличие и perPage; заменить только `q` и сбросить page. |
| Отправить с другой страницы | Перейти на `/catalog?q=...` без заимствования чужих фильтров. |
| Отправить пустой/пробельный запрос | Открыть каталог без `q`; если уже в каталоге — убрать только `q`, сохранив фильтры и сбросив страницу. Пустая быстрая панель не выводит весь каталог. |
| Открыть конкретное предложение | Обычная внутренняя ссылка на растение с точными параметрами через существующий `productSelectionHref`. |

Быстрая выдача ищет **по всему каталогу**, независимо от фильтров фоновой страницы. Полная выдача из текущего каталога учитывает сохранённые фильтры. Для понятности возле перехода уместно короткое пояснение «С учётом фильтров каталога», если они активны: счётчик быстрой выдачи относится ко всему каталогу. Это уточнение поведения, не основание переделывать визуальную концепцию.

После удаления старого input из каталога оставить заметный способ видеть и снять применённый запрос, например компактное «Поиск: туя» с отдельной очисткой. Очистка применённого запроса меняет `q`, сохраняет остальные фильтры и сбрасывает page. Существующая «Сбросить фильтры» не должна незаметно превращаться в сброс поиска.

Не менять текущую семантику поиска: NFKC, регистр, ё/е, trim, разбиение по пробельным символам, AND по частям имени, литеральная пунктуация. Поиск по горшкам, возрасту, описанию, опечаткам и новый ранжирующий движок в задачу не входят.

Предлагаемые технические defaults: начинать после первого непустого символа; debounce около150 ms; в быстрой выдаче до4 групп, раскрывать все реальные предложения выбранной группы; общий счётчик считать до ограничения preview. Порядок групп стабильный, по минимальной доступной цене, затем по имени; естественный порядок строк размера/возраста/горшка сохранять. Если у группы всё под заказ, показать самое дешёвое предложение с «Под заказ», не выдумывать наличие. При одинаковой цене применять детерминированный порядок. Эти правила требуется покрыть тестами; цены и количество из макетов не хардкодить.

Пустой запрос: спокойное начальное состояние с предложением ввести название; не добавлять «популярные» запросы без данных. Для непустого запроса нужны loading, результаты, ничего не найдено и ошибка с повтором. Старый запоздавший ответ не подменяет новый запрос. При ошибке/нуле результатов пользователь может изменить текст, закрыть панель или перейти в каталог. Enter не должен отправлять запрос посреди IME-композиции.

### Неочевидные детали данных

В DBProduct `variant.id` — локальный идентификатор группы значения, создаваемый адаптером; это **не Payload ProductVariant.id**. `pot.id` в нормализованной модели присваивается из исходного ProductVariant.id, а не из справочника ProductPot. Нельзя предполагать смысл ID по его имени. Точная selection — пара `{variantId, potId}` по существующему контракту. Для UI-ключей групп использовать itemId, для конкретного предложения — его настоящий стабильный ID/пару, не индекс строки.

Чтобы получить предложения, пройти только существующие `product.variants.flatMap(variant => variant.pots...)`, сохраняя принадлежность pot своему variant. `valueType` различает size/age/none; возрастная подпись собирается из value и postfix. Форматирование подписи в интерфейсе не должно менять значение URL.

Ссылки строить через productSelectionHref и отдавать относительными внутренними href, без зашитого production-домена. Примеры контракта: `/catalog/<slug>?size=60-70&pot=C2`, `?age=4+%D0%B3%D0%BE%D0%B4%D0%B0&pot=C2`, `?pot=C3`. После перехода должны совпасть параметры, цена, наличие и фото. Неверная ссылка не должна маскироваться запасным первым вариантом: проверить resolveProductSelection на фактической ссылке.

Изображение свёрнутого результата — из показанного предложения (его pot.images); если фото нет — действующий category placeholder. Не брать чужой сорт ради заполнения картинки. `product.image` в DBProduct является fallback, не гарантированным фото выбранного предложения.

`src/app/(frontend)/catalog/products.ts` содержит старый статический массив: **не брать из него товары/цены для нового поиска**. Допустимы переиспользуемые типы; факты — из Payload через существующий адаптер/новую компактную проекцию. Макетные примеры: Смарагд — размер+горшок, Даника — горшки, Блюкроп/Дюк — возраст+горшок, включая «Под заказ». Числа «10/23» и цены в PNG — снимок на момент дизайна; текущую БД надо проверить заново.

## 6. Границы архитектуры и реализации

Рекомендуемая схема: единый контроллер общего поиска возле Header + адаптивная панель + небольшие компоненты группы и предложения + чистая функция подготовки выдачи. Конкретные имена файлов и организация остаются за исполнителем. Состояние каталога и черновика не связывать через изменение URL на каждом символе.

Для данных предпочтительна ленивая серверная загрузка по открытию/запросу с типизированным компактным ответом, например группы `{itemId, slug, name, offers:[...]}` и общие totals. Не грузить полный DBProduct с описаниями, уходом и всеми медиа в каждую страницу. Переиспользовать правила нормализации и реальные связи каталога; не создавать второй расходящийся каталог. Валидация длины запроса/лимита, отмена/игнорирование устаревшего ответа и понятные loading/error обязательны. При выборе endpoint учитывать существующий Payload catch-all `/api/[...slug]`, не ломать REST/админку. Пользовательские данные и административные поля в публичный DTO не передавать. Схема БД для этой задачи не требует изменения.

На десктопе модалка должна быть привязана к настоящему положению поля в container, а не только к x280 из1440-макета. Ширина720 ограничивается свободным viewport. Фон инертен, scroll-lock возвращает исходное положение, фокус остаётся в панели. На touch-экранах учитывать dynamic viewport/появление клавиатуры; при раскрытии группы input.blur() не должен терять действие нажатия. Системную клавиатуру в автоматическом desktop browser полностью проверить нельзя — обозначить границу проверки и по возможности проверить на устройстве.

Существующий общий header сейчас целиком sticky: для утверждённого поведения второй строки это потребуется изменить структурно. Нельзя просто поставить второе поле внутрь текущего sticky-контейнера и считать прокрутку реализованной. Открытие поиска и меню должны быть согласованы: не оставлять две перекрывающие панели одновременно. Route change закрывает поиск; resize меняет раскладку без потери query/фокуса и без двух копий активного input.

Семантика: dialog с доступным названием, input type=search с настоящим label и enterKeyHint=search, видимое закрытие, aria-expanded на раскрытии, тихое aria-live для статуса. Не присваивать всем строкам listbox/option, если внутри независимые ссылки и кнопки. Поддержать Tab/Shift+Tab, Enter, Escape, reduced-motion. Визуально компактный input не должен ухудшать область попадания на touch; при необходимости расширить hit-area невидимым отступом, сохраняя макетные40 px.

Использовать существующие зависимости и UI-примитивы. В проекте есть пакет radix-ui, но готового `src/components/ui/dialog.tsx` при подготовке не было; проверить доступные примитивы перед добавлением. Не добавлять библиотеку/поисковый сервис без необходимости. Новый search-код тестировать по его поведению, не подгонкой снимков под внутреннюю реализацию.

- Не изменять Figma, PRODUCT.md, существующие несвязанные страницы и тексты. Деплой/пуш/публикация не запрошены.

## 8. Приёмка и проверки

### Поведение

1. Открытие с главной, каталога, статьи и страницы растения; фоновая страница остаётся исходной. На каталоге ввод, очистка черновика и отмена не меняют q/фильтры/карточки/page/scroll.
2. Enter, лупа и CTA дают одинаковый переход. Из каталога сохраняются фильтры/perPage, page сбрасывается; с остальных страниц — корректный `/catalog?q=...`. Пустой submit и очистка применённого q работают по разделу3.
3. Поиск с несколькими словами, разным регистром, ё/е, пробелами, пустой строкой, нулём совпадений. Совпадения в панели и каталоге основаны на одном matcher.
4. Все три типа вариантов. Раскрытие не переставляет группы, не образует несуществующие пары и не является переходом по основной ссылке. Проверить случай, когда самый дешёвый вариант под заказ, но есть более дорогой в наличии, и когда под заказ все.
5. Три deep link: размер+горшок, возраст+горшок, только горшок. На странице растения правильные параметры, фото, цена, наличие; обновление страницы и Back не теряют выбор/состояние каталога.
6. Закрытие крестиком/Escape/подложкой, возврат фокуса и прокрутки. Раскрытие с touch-клавиатурой, resize/поворот, открытое меню, запоздавший ответ и ошибка/повтор не блокируют поиск.
